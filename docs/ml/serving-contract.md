# Serving contract (PM-03)

How a forecast gets from live data to a map cell. This is the boundary between GEO (features, interpolation), ML (model), OPS (pipeline) and API (reads). It fixes names, units and rules so those four can build in parallel. It does not change the model.

| | |
|---|---|
| Model | `baseline_v2` ([model card](../models/baseline_v2.md)), served exactly as trained |
| Feature list | `ml.feature_columns.FEATURES_V2`, rendered in [`features.json`](features.json) |
| Horizons | 1, 3, 6, 12, 24 h. Fixed. |
| Schema delta | migration `0004_serving_contract.py` |
| Decided | 2026-10-12 (monitor-first), 2026-10-13 (the rules below) |

## 1. Why two stages

baseline_v2's `pm25_lag_*` features are **the monitor's own readings**, and the model is anchored on that persistence (97.8% of training labels are at distance 0). A grid cell has no monitor, so v2 cannot run there as trained. So:

- **Stage A, model at monitors.** Run baseline_v2 unchanged at every forecast-point monitor.
- **Stage B, interpolate to the grid.** A cell's forecast is an inverse-distance-weighted (IDW) mean of nearby Stage A forecasts.

ML-02 (#43) tests a model trained on leave-one-out IDW lags that can run directly at cells. It replaces Stage B only if it wins on held-out monitors. If it does, this document gets a new revision; Stage A and the schema stay.

```
live feeds ──► features (monitor points) ──► predict_v2 ──► forecasts (source v2 / persistence / fallback)
                                                                  │
                                                       IDW (k=4, p=2, 50 km)
                                                                  ▼
                                                  forecasts at grid cells (source idw)
```

## 2. Feature vector

The contract is `ml.feature_columns.FEATURES_V2`, in that order. [`features.json`](features.json) has, for every feature, its dtype, unit, null rule, training definition and live definition. It is generated by `backend/scripts/gen_features_json.py`, and `tests/test_serving_contract.py` fails if it goes stale or disagrees with `ml.feature_columns`.

**The caller supplies the 22 columns in `input_columns`.** `horizon_hours` is set by `predict_v2.predict` from its `horizon` argument, and `persistence`, `trend_1_3`, `trend_1_6`, `ratio_1_24` are added by `ml.features.add_derived`, the same function training calls. Never compute them elsewhere.

Dtypes follow `dataset_build/build_v1.py`: `float32` for continuous features, `int16` for `active_fire_count_200km` and `day_of_year`, `int8` for `month` and `horizon_hours`, `bool` for `smoke_season`. Derived columns are `float64`.

### Sources and windows

| Group | Training (`dataset_build`, `features/`) | Live source | Window / rule |
|---|---|---|---|
| Fire (5) | `fire_detections`, `satellite = 'VIIRS_SNPP'` | VIIRS **SNPP NRT** only. The connector tags NRT and archive rows alike as `VIIRS_SNPP`, so the query is identical. | Detections with `issue_time − 72 h ≤ detected_at < issue_time` within 200 km of the point. Bbox + 200 km only limits what is loaded. |
| Weather (8) | `weather_observations` from NCEI Global Hourly | `weather_observations` from **NWS station observations** (DATA-06) | Nearest station to the point; latest report with `issue_time − 3 h ≤ valid_at ≤ issue_time`. Station ids are ICAO in both. |
| Lags (5) | AirNow regulatory `RawConcentration` at the point's own monitor | Same, from `observations` (`correction = 'regulatory'`) | Reading with `valid_at` exactly `issue_time − {1,3,6,12,24} h`; no nearest-hour fallback. Per-site time offsets are applied at ingest (`airnow_time_offsets.py`), and values in [−5, 0) are clamped to 0. |
| Calendar (4) | `issue_time` (UTC) and the point's longitude | same | `local_solar_hour = (UTC hour + longitude / 15) mod 24` |

### Weather field mapping (NCEI → NWS)

Training and live use the same station-selection and 3 h rules. Only the field decoding differs:

| Feature | Training (NCEI ISD) | Live (NWS `/stations/{id}/observations`) |
|---|---|---|
| `wind_speed_ms` | `WND` speed, m/s | `windSpeed`, converted to m/s using its `unitCode` (`wmoUnit:km_h-1` ÷ 3.6) |
| `wind_dir_sin/cos` | `WND` direction (from), calm → null | `windDirection` (from). **Set to null whenever speed is 0**, to match NCEI calm |
| `wind_alignment` | `cos(fire_bearing_deg − wind_dir_deg)`: 1 means the fire is directly upwind | same formula; null if either input is null |
| `temp_c` | `TMP`, °C | `temperature`, °C |
| `rh_pct` | `relative_humidity_from_dewpoint(TMP, DEW)` | same function on `temperature`, `dewpoint`. **Do not use NWS `relativeHumidity`.** |
| `pressure_hpa` | `SLP`, hPa; null if ≤ 800 | `seaLevelPressure` ÷ 100. **Not `barometricPressure`** (station pressure). Null if missing or ≤ 800. |
| `precip_1h_mm` | ISD `AA1–AA4` 1 h accumulation | `precipitationLastHour` in mm |

NWS unit codes must be read per observation, never assumed. DATA-06 owns the decoding and tests it against these rows.

### Missing data

Matches the null handling in the [dataset card](../datasets/smokesense_v1.md#null-rate-per-feature). Missing weather and lags are **left null** (XGBoost handles NaN, and the model saw 4–59% nulls in training). Nothing is imputed at serving time.

| Case | Behaviour |
|---|---|
| No fire in the 72 h / 200 km window | `nearest_fire_dist_km = 9999`, `fire_bearing_sin/cos = 0`, `total_frp_200km = 0`, `active_fire_count_200km = 0`; `wind_alignment` null |
| No station report in the 3 h window | all weather features null |
| Calm wind | `wind_dir_sin/cos` and `wind_alignment` null |
| No `pressure_hpa` / `precip_1h_mm` in the report | null (not 0) |
| A lag has no reading at that hour | that lag null; trends and ratio null accordingly |
| `lag_1h`, `lag_3h` and `lag_6h` all null | `persistence` null → `predict_v2` serves the v1 **fallback** model, `source = 'fallback'` |
| Fire feed down entirely | **Do not run.** An empty frame would read as "no fire" and is not the same input. OPS-04 skips the cycle and keeps the last forecasts. |

### Issue time

`issued_at` is the top of a UTC hour `H`. Every feature uses only data with timestamp ≤ `H` (fires strictly before `H`), exactly as in training. Lag-1 is the reading labelled `H − 1 h`, which AirNow publishes after that hour ends. OPS-04 therefore waits until it is ingested or a cutoff passes (proposed: `H + 45 min`; OPS-04 sets the number). Past the cutoff the lag is null and the rules above apply.

### Known live-vs-training gaps

These do not break "same value for the same inputs", but they mean the live inputs may differ from training inputs. Track them in shadow evaluation (ML-04 / OPS-04):

- **FIRMS NRT latency.** NRT detections arrive up to a few hours after the overpass; training counted every detection with `detected_at < issue_time`. Live fire counts for the latest hours can be lower.
- **NRT vs archive.** Training used the reprocessed `_SP` archive; live uses NRT. Detections can differ slightly.
- **NWS precipitation.** NCEI gives null when there is no 1 h group. If NWS reports 0 where NCEI would be null, `precip_1h_mm` shifts. Keep NWS nulls as null and check the null rate against the card (≈ 59%).
- **Station pressure vs sea level.** Using the wrong NWS pressure field changes `pressure_hpa` by ~100 hPa at altitude (§ mapping).

## 3. Stage A: forecast-point monitors

A monitor is a Stage A forecast point when **all** hold:

1. `monitors.source = 'airnow'`, `active`, `location_type = 'outdoor'`.
2. `in_california_scope(monitors.aqs_code)` (`app/core/scope.py`, decision #17).
3. It has a regulatory PM2.5 reading in the last 24 h. Without one every lag is null and `fallback` would run on pure weather and fire features.

Each has a `forecast_points` row with `kind = 'monitor'` and `monitor_id` set. `geom` is the monitor's location. Its `nearest_monitor_dist_km` is 0.

**Which id is which.** In the database, a monitor point has its own UUIDv7 `forecast_points.id` and links to its monitor through `monitor_id`. DATA-04's `forecast_point_id` is `monitors.external_id`. Do not set `forecast_points.id = external_id`. When comparing serving output with training rows, join `forecast_points.monitor_id → monitors.id` and use `monitors.external_id`. The API uses `forecast_points.id` as the forecast point id, with `aqs_code` and the monitor name as readable fields.

**Moved monitors.** When a monitor moves more than 500 m, `monitors` gets a new row and the old one is deactivated (`docs/schema.md`). The old monitor's forecast point is set `active = false` and stops forecasting, keeping its history; the new monitor gets a new point. Stage B only uses active points.

## 4. Stage B: interpolation to grid cells

Inputs are the Stage A forecasts for the same `issued_at` and `horizon_hours`. Each horizon is interpolated independently. For each `kind = 'grid_cell'` forecast point (centroid `geom`):

| Parameter | Value | |
|---|---|---|
| Distance | great-circle, haversine, R = 6371.008 km (the same as `features/spatial.py`), to the cell centroid | |
| Eligible monitors | Stage A rows with `source ∈ {'v2', 'persistence'}` | `fallback` monitors have no reading in the last 6 h, so they are likely offline and would project stale conditions. They keep their own forecast but never feed a cell. |
| Max radius | **50 km** | |
| k | **4** nearest eligible monitors within the radius | |
| Weights | `w = 1 / d²`, with `d = max(distance_km, 1.0)` | The 1 km floor stops a division by ~0. |
| Value | `Σ wᵢ·pm25ᵢ / Σ wᵢ`, in linear µg/m³ | |
| One monitor in range | use it (weight 1). Still a forecast. | |
| **No monitor in range** | **No forecast.** No `forecasts` row is written, the API returns "no forecast" for the cell, and the map leaves it empty. There is no low-confidence fallback. | |

Output row: `source = 'idw'`, `model_key` = the Stage A model's key, `nearest_monitor_dist_km` = distance to the nearest *eligible* monitor in range (the real distance, not the 1 km floor), and `feature_snapshot = {"monitors": [{"id", "distance_km", "weight", "pm25", "source"}, …]}` so the "Why?" panel and debugging can see the inputs. The UI treats `nearest_monitor_dist_km > 25` as lower confidence (`docs/schema.md`).

The defaults above are a starting point. GEO-03 may tune them against leave-one-monitor-out error, but any change is a revision of this document. ML-02's comparison uses the same held-out monitors.

## 5. Model interface

```python
def predict(features: pd.DataFrame) -> pd.DataFrame: ...
```

- **In:** one row per Stage A forecast point: `forecast_point_id`, `issued_at` (UTC), and the 22 `input_columns` of `features.json`. No `horizon_hours`, no derived columns.
- **Out:** one row per (point, horizon in 1/3/6/12/24):

| Column | Type | Notes |
|---|---|---|
| `forecast_point_id` | str | as in the input |
| `horizon_hours` | int | 1, 3, 6, 12 or 24 |
| `pm25_predicted` | float | µg/m³, ≥ 0 (`predict_v2`'s `pm25`) |
| `source` | str | `predict_v2`'s `source`: `v2`, `persistence` or `fallback` |
| `model_key` | str | `model_versions.model_key` of the loaded model |
| `issued_at` | datetime (UTC) | as in the input |
| `target_time` | datetime (UTC) | `issued_at + horizon_hours` |

It follows `release.json` per horizon through `ml.inference.predict_v2.predict`. ML-04 (#45) wraps it as `ml.inference.service.InferenceService` (`from_registry(registry, name=… | model_key=…)` or `from_dir(path, model_key)`, then `.predict(features)`). It checks the input against the loaded model's `features.json`:
- missing columns are rejected, naming them;
- the input columns must be in `features.json` order, and a misordered frame is rejected, naming the positions;
- extra columns are dropped with a warning, including any derived column the caller computed;
- `issued_at` must be timezone-aware and is converted to UTC.

A model whose `release.json` serves anything other than `v2` or `persistence` is refused at load (decision #48). Rows are not written when `pm25_predicted` is NaN. `exceeds` is not part of the contract. It is only needed for alerts (Phase 4). The per-horizon thresholds (`release.json`: 31.5 / 29.5 / 25.5 / 21.5 / 20.0, with 35.5 where persistence is served) are copied into `model_versions.thresholds` when the model is registered, so the API reads them from the database by `model_key` and never opens model files. These are the **model's alert thresholds, tuned for F1**, not the EPA AQI category cutoffs; the UI must not present them as AQI categories. Stage B (§4) is a separate step that turns these rows into `source = 'idw'` rows.

The model is always loaded by explicit `model_key`, never "newest".

## 6. Artifact layout

Updated 2026-10-28 to match the OPS-02 registry (PR #68).

The registry (`backend/mlops/registry.py`, [`docs/mlops/registry.md`](../mlops/registry.md)) stores one model directory as one deterministic `.tar.gz` (sorted files, mtime 0, fixed modes, no gzip filename, so the same contents always give the same sha256). For baseline_v2 that directory is `backend/data/models/packaged/baseline_v2/` (not in git, written by `ml.tools.package_baseline_for_registry`):

```
release.json          per horizon: serve (v2 or persistence), threshold
thresholds.json
features.json         the baseline's own feature list
params.json
metrics.json          NaN written as null (JSONB rejects NaN)
manifest.json         dataset sha256, git commit, package block (source hashes, serve per horizon)
model_h{1,3,6,12,24}.json      residual boosters
fallback_h{1,3,6,12,24}.json   v1 direct boosters
```

`register` reads the metadata, packs the folder, and uploads it to the configured backend:

| `REGISTRY_BACKEND` | Archive location (`artifact_uri`) |
|---|---|
| `local` (default) | `file://<REGISTRY_LOCAL_DIR>/baseline/v2.tar.gz` (absolute path; default dir `backend/data/registry`) |
| `s3` (S3 or Cloudflare R2) | `s3://<REGISTRY_S3_BUCKET>/<REGISTRY_S3_PREFIX>/baseline/v2.tar.gz` (defaults `smoke-sense`, `models`) |

Local cache: `<REGISTRY_CACHE_DIR>/<artifact_sha256>/` (default `backend/data/registry_cache`). `materialize` / `load_production` fill it after checking the downloaded archive against `artifact_sha256`, and that folder is what `predict_v2.predict(..., model_dir=)` receives. A damaged cache is discarded and fetched again.

`model_versions` row (table from migration 0001, `thresholds` from 0004; no change):

| Column | Value |
|---|---|
| `model_key` | `{model_name}/{version}`, e.g. `baseline/v2` |
| `model_name`, `version` | `baseline`, `v2` (`--name`, `--version`; letters, digits, `.`, `_`, `-` only) |
| `algorithm` | `--algorithm`, here `xgboost-residual-on-persistence` |
| `artifact_uri` | where the registry stored the archive (table above) |
| `artifact_sha256` | sha256 of the `.tar.gz` archive; checked on every load and before `promote` / `rollback` |
| `feature_list` | `features.json` → `features` (required) |
| `thresholds` | each horizon's `threshold` in `release.json` (required), e.g. `{"1": 35.5, "3": 29.5, "6": 25.5, "12": 21.5, "24": 20.0}` |
| `hyperparameters` | `params.json` |
| `backtest_metrics` | `metrics.json` |
| `training_data_hash` | `manifest.json` → `dataset.data_sha256` (`6799c405…`) |
| `training_data_uri`, `notes` | `--training-data-uri` (`data/datasets/smokesense_v1`), `--notes` |
| `status` | `shadow` when registered → `production` on `promote` → `retired` when another version is promoted; `rollback` returns the latest retired version to `production` and the replaced one to `shadow`. At most one `production` row per `model_name` (unique index `one_production`). |

The columns from `feature_list` to `training_data_hash` are filled by `mlops.registry.read_metadata` from the model folder.

`model_key` is the registry key from `mlops.registry` (`model_name/version`).

## 7. Schema delta

`model_versions` and `forecasts` already exist (migration 0001). Migration `0004_serving_contract.py` adds only what is missing:

| Table | Change | Why |
|---|---|---|
| `forecast_points` | `kind` also allows `'monitor'`. `'grid_cell'` is kept (no rename). | Stage A points are monitors. |
| `forecast_points` | `monitor_id TEXT REFERENCES monitors(id)`, unique where not null; `CHECK ((kind = 'monitor') = (monitor_id IS NOT NULL))` | Links a point to its monitor. |
| `forecast_points` | `cell_geom GEOGRAPHY(POLYGON, 4326)` + GiST index | The cell polygon for the map. `geom` stays the centroid. GEO-02 fills it. |
| `forecasts` | `source TEXT NOT NULL CHECK IN ('v2','persistence','fallback','idw')` | Says how each value was made. |
| `forecasts` | `nearest_monitor_dist_km` NOT NULL, CHECK `> 0` → `>= 0` | A monitor point is its own nearest monitor (0 km), and every row has a distance (cells with no monitor in range get no row). |
| `model_versions` | `thresholds JSONB` | Per-horizon alert thresholds, so the API never reads model files. |

The ORM (`app/models/`) and `docs/schema.md` are updated to match.
